## 1. Введение {#1-introduction}

### 1.1 Назначение документа {#11-document-purpose}

Настоящий документ представляет собой Спецификацию требований к программному обеспечению (SRS) для десктопного приложения «UtilitySmart». Его главная задача — четко определить границы проекта и зафиксировать, **ЧТО** именно должна делать система, оставляя пространство для инженерных решений относительно того, **КАК** это будет реализовано. Документ выступает главным ориентиром для команды разработки, тестировщиков, заказчика и преподавателя.

### 1.2 Область применения продукта {#12-product-scope}

**«UtilitySmart» 0.1** — десктопное приложение для ведения учета и расчета коммунальных платежей. Пользователь вводит текущие показания счетчиков, а система автоматически рассчитывает сумму к оплате на основе сохраненных тарифов и ведет историю расчетов.

**Входит в область применения:**
* Настройка и редактирование тарифов (вода, электроэнергия).
* Ввод текущих и предыдущих показаний счетчиков.
* Автоматический расчет суммы к оплате.
* Сохранение истории расчетов в локальную базу данных.
* Экспорт истории платежей в файл (CSV).

**Не входит в область применения (в текущей версии):**
* Онлайн-оплата услуг.
* Интеграция с внешними API (сайты ЖКХ, банки).
* Синхронизация данных через интернет (облачные хранилища).
* Мобильное приложение (система реализуется исключительно как Desktop-решение).

Документ описывает десктопное приложение **«UtilitySmart»** и структурирован для последовательного ознакомления: Введение (назначение, границы, глоссарий); Обзор продукта (контекст, функции, пользователи); Требования (детальные, верифицируемые требования); Верификация (методы проверки); Приложения (справочные материалы). ## 2. Обзор продукта {#2-product-overview}

### 2.1 Перспектива продукта {#21-product-perspective}

Приложение «UtilitySmart» — новый самостоятельный продукт. Ранее расчеты за коммунальные услуги производились вручную (на бумаге или в обычном калькуляторе), что часто приводило к арифметическим ошибкам и занимало время. Приложение объединяет в себе базу тарифов, калькулятор и архив показаний в едином локальном интерфейсе.

**Внешние системы и зависимости:**
* В текущей версии приложение не использует внешние API и сетевые сервисы (за исключением стандартных библиотек C++ и Qt).
* В качестве хранилища данных используется локальный файл базы данных SQLite.

### 2.2 Функции продукта {#22-product-functions}

* Ввод и настройка тарифов на коммунальные ресурсы (холодная/горячая вода, электричество).
* Ввод текущих показаний счетчиков.
* Автоматический расчет суммы к оплате (с учетом разницы между предыдущими и текущими показаниями).
* Сохранение результатов расчетов в локальную базу данных.
* Просмотр истории расчетов за предыдущие месяцы.
* Экспорт данных в файл формата CSV.

### 2.3 Ограничения продукта {#23-product-constraints}

* **Только десктопная версия:** без поддержки веб-браузеров и мобильных ОС.
* **Язык интерфейса:** русский.
* **Локальность:** приложение не отправляет данные в интернет.
* **Технологический стек:** Язык **C++ (стандарт C++17)**, фреймворк **Qt 6** (модуль Widgets), база данных **SQLite**, система сборки **CMake**.

### 2.4 Характеристики пользователей {#24-user-characteristics}

| Роль | Описание | Права доступа |
| :--- | :--- | :--- |
| **Пользователь (Клиент)** | Собственник или арендатор жилья, оплачивающий коммунальные счета | Полный доступ ко всем функциям приложения (настройка тарифов, ввод данных, просмотр истории) |

### 2.5 Допущения и зависимости {#25-assumptions-and-dependencies}

* **Операционная система:** Пользователь использует ОС Windows 10 или выше (или Linux).
* **Данные:** Пользователь знает актуальные тарифы и имеет доступ к физическим счетчикам для снятия показаний.

### 2.6 Распределение требований {#26-apportioning-of-requirements}

| Компонент (Модуль) | Связанные требования (ID) | Краткое описание зоны ответственности |

## 3. Требования {#3-requirements}

### 3.1 Внешние интерфейсы {#31-external-interfaces}

#### 3.1.1 Пользовательские интерфейсы {#311-user-interfaces}

**REQ-INT-001: Главное окно (Калькулятор)**
* **Title:** Отображение полей ввода и результатов.
* **Statement:** Система должна предоставлять главное окно, содержащее поля для ввода текущих показаний (вода, электричество), кнопку «Рассчитать», а также блок для вывода итоговой суммы к оплате.
* **Rationale:** Это основной рабочий экран, где происходит 90% взаимодействия с пользователем.
* **Verification Method:** Demonstration.

**REQ-INT-002: Окно настроек тарифов**
* **Title:** Настройка стоимости ресурсов.
* **Statement:** Система должна предоставлять отдельное окно (или вкладку) для изменения действующих тарифов (например, стоимость 1 кВт/ч или 1 куб. м воды).
* **Rationale:** Тарифы меняются несколько раз в год, пользователь должен иметь возможность обновить их без переустановки программы.
* **Verification Method:** Demonstration.

#### 3.1.2 Аппаратные интерфейсы {#312-hardware-interfaces}

**REQ-INT-003: Работа с периферией**
* **Statement:** Система должна корректно отображаться на мониторах с разрешением от 1280x720 и выше.
* **Verification Method:** Test.

#### 3.1.3 Программные интерфейсы {#313-software-interfaces}

**REQ-INT-004: Интерфейс базы данных**
* **Statement:** Система должна использовать локальную библиотеку SQLite для сохранения и чтения данных без необходимости установки отдельного сервера БД.
* **Verification Method:** Inspection.

### 3.2 Функциональные требования {#32-functional}

**REQ-FUNC-001: Ввод и валидация показаний**
* **Statement:** Система должна позволять пользователю вводить текущие показания счетчиков. Система должна блокировать ввод буквенных символов и отрицательных чисел.
* **Acceptance Criteria:** При попытке ввести текст в поле показаний, ввод игнорируется. Текущее показание не может быть меньше предыдущего (сохраненного в базе).
* **Verification Method:** Test.

**REQ-FUNC-002: Расчет стоимости**
* **Statement:** Система должна автоматически рассчитывать итоговую сумму к оплате по формуле: `Сумма = (Текущее показание - Предыдущее показание) * Тариф`.
* **Acceptance Criteria:** При нажатии кнопки «Рассчитать» на экране отображается корректная сумма, округленная до двух знаков после запятой.
* **Verification Method:** Test.

**REQ-FUNC-003: Управление тарифами**
* **Statement:** Система должна сохранять измененные тарифы в базе данных.
* **Acceptance Criteria:** После изменения тарифа и перезапуска программы, расчет производится по новому тарифу.
* **Verification Method:** Test.

**REQ-FUNC-004: Сохранение истории**
* **Statement:** Система должна сохранять в базу данных дату расчета, введенные показания и итоговую сумму.
* **Acceptance Criteria:** В окне истории отображаются все произведенные ранее расчеты в хронологическом порядке.
* **Verification Method:** Test.

**REQ-FUNC-005: Экспорт в CSV**
* **Statement:** Система должна позволять сохранять таблицу истории расчетов в файл формата .csv.
* **Acceptance Criteria:** Экспортированный файл открывается в Microsoft Excel без потери данных и правильной кодировке (UTF-8).
* **Verification Method:** Test.

### 3.3 Качество обслуживания {#33-quality-of-service}

#### 3.3.1 Производительность {#331-performance}

**REQ-PERF-001: Время расчета**
* **Statement:** Время от нажатия кнопки «Рассчитать» до отображения результата не должно превышать **100 миллисекунд**.
* **Verification Method:** Test.

#### 3.3.2 Безопасность {#332-security}

**REQ-SEC-001: Локальность данных**
* **Statement:** Все персональные данные и показания счетчиков должны храниться исключительно на локальном диске пользователя (в файле базы данных). Приложение не должно передавать данные по сети.
* **Verification Method:** Inspection.

#### 3.3.3 Надёжность {#333-reliability}

**REQ-REL-001: Целостность данных**
* **Statement:** При аварийном закрытии приложения (например, при отключении электроэнергии) база данных не должна повреждаться. Записи должны сохраняться только после успешного завершения транзакции.
* **Verification Method:** Test.

#### 3.3.4 Доступность {#334-availability}

**REQ-AVAIL-001: Локальная доступность**
* **Statement:** Приложение не зависит от серверов и доступно 100% времени, пока работает операционная система пользователя.
* **Verification Method:** Analysis.

#### 3.3.5 Наблюдаемость {#335-observability}

**REQ-OBS-001: Логирование ошибок**
* **Statement:** При возникновении критических ошибок (например, недоступность файла БД) приложение должно выводить понятное сообщение в графическом интерфейсе и вести лог-файл в папке приложения.
* **Verification Method:** Test.

### 3.4 Соответствие стандартам {#34-compliance}

**REQ-COMP-001: Кодировка**
* **Statement:** Все текстовые файлы (экспорт, логи) должны использовать кодировку UTF-8 для корректного отображения кириллицы.
* **Verification Method:** Inspection.

### 3.5 Проектирование и реализация {#35-design-and-implementation}

#### 3.5.1 Установка {#351-installation}

**REQ-INST-001: Портативность**
* **Statement:** Приложение должно распространяться в виде архива с исполняемым файлом (.exe) и необходимыми библиотеками (DLL), не требуя сложной установки (Portable-версия).
* **Verification Method:** Demonstration.

#### 3.5.2 Сборка и поставка {#352-build-and-delivery}

**REQ-BUILD-001: Система сборки**
* **Statement:** Сборка проекта должна осуществляться с помощью системы CMake.
* **Verification Method:** Test.

#### 3.5.4 Сопровождаемость {#354-maintainability}

**REQ-MAINT-001: Архитектура MVC**
* **Statement:** Код приложения должен быть разделен на слои Модели (данные и логика), Представления (интерфейс Qt) и Контроллера (связующее звено).
* **Verification Method:** Inspection.

### 3.6 ИИ/МО {#36-aiml}

*В текущей версии проекта «UtilitySmart» компоненты искусственного интеллекта и машинного обучения не используются.*
